# Plugin evals in CI

Decision record for [#436](https://github.com/dfadler/agent-config/issues/436). Full research and the per-question rationale are in the
[recommendation comment](https://github.com/dfadler/agent-config/issues/436#issuecomment-5940264329);
CLI facts are from the [plugin-evals docs](https://code.claude.com/docs/en/plugin-evals).

Workflow: `.github/workflows/plugin-evals.yml` (#582); result checker: #583. Recommendation:

- **Trigger:** `workflow_dispatch` only. The weekly run is a local scheduled task (see Alerting). Never `schedule` or `pull_request` (public repo, `--trust-plugin`, paid key).
- **Scope:** plugins that have `evals/` (32 as of 2026-11-03, `ls -d plugins/*/evals`), one matrix entry each, after #442 removes vacuous cases.
- **Gate:** hard-fail on the run-evals wrapper's exit code. The wrapper fixes `--threshold` at 1 (every grader must pass), so the earlier 0.8 start is dropped; #584 calibrates Δ, not a pass threshold. Δ is gated at plugin level with `--delta-floor 0.14` (#736, replacing the per-case `--delta-floor 0` of #585): the checker takes per-case verdicts from `diagnose()` (standard error), and the run is a regression only when the mean Δ over cases with a Δ is below +0.14. The wrapper writes one result file per case, so the checker takes every file of the run in one call and pools the cases; called once per file, as the workflow first did, each call saw one case and the floor could never fail a run. The per-case rule (`delta < 0` on any case) falsely failed an unchanged plugin 30 to 50% of the time, rising with case count. The gate is advisory (warn, exit 0) until a plugin has 16 cases (`MIN_GATE_CASES` in `check-plugin-eval.ts`, the low end of the issue's 16 to 26), since +0.14 needs about 80 runs per arm in total. Per-case verdicts, a missing `delta` and the CLI exit code (`--threshold 1`) are unchanged in meaning: verdicts warn, a missing `delta` is no signal, a non-zero CLI exit is a regression unless the gate is active (16+ cases with a Δ) and met, when the mean Δ decides and the cases under the threshold only warn (#906: 25 of 32 plugins failed a run on one flaky case each at threshold 1). The checker also prints the with-plugin mean score and the all-runs-pass share (cases whose with-plugin runs all scored 1).
- **Runner:** the `run-evals.ts` wrapper at the `standard` tier (every case, 3 runs, with and without the plugin, `--max-cost-usd 25`, `--no-publish`, models pinned in the wrapper). It applies each case's `grants.yaml` grants, which a raw `claude plugin eval` call would not, so cases that need Bash can pass. The workflow does not use `--changed`; a job that did would get no `aggregate-result.json` when the changed files map to no case (the wrapper exits 1, or 0 with `--changed-allow-empty`, before running anything), and the Check step then fails as inconclusive (exit 7), so such a job must skip the check when nothing was selected.
- **Invalid runs:** exit 2, `partial: true`, `skippedPaidGraders`, or any `arms.with[].error` fail the job as inconclusive, not as a regression. So does an implausible result (#734, #735): empty `cases`, a case with no with-arm runs, a wrong `schemaVersion`, dropped malformed entries, a run scoring 0 with no grader detail, or every run of the whole run (all result files pooled) scoring 0. One case that scores 0 on every run is not a dead run: the diagnosis names it.
- **Auth:** `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`, a one-year token for a Pro, Max, Team or Enterprise plan) in a protected `plugin-evals` environment, per the [authentication docs](https://code.claude.com/docs/en/authentication#generate-a-long-lived-token). Replaces the earlier spend-capped `ANTHROPIC_API_KEY` plan. Consequences:
  - Runs count against the plan's usage limits, shared with interactive use. `--max-cost-usd` is a list-price ceiling, not a spend cap. CI passes 25 (#648) because the standard tier's flat $5 stopped four big suites at exit 7 with 1 to 11 cases unrun (2026-10-12 and 10-19 runs); the interactive tier ceilings are unchanged. $25 is a ceiling, not a spend: the big suites spent about $5 each when they hit the old ceiling, the small ones $0.7 to $2.0.
  - A run that hits the usage limit scores 0 and is not marked `partial` ([troubleshooting](https://code.claude.com/docs/en/plugin-evals)); the checker treats an `arms.with[].error` or `arms.without[].error` as inconclusive (the without-arm check lands in #599), so it shows as exit 7, not a regression. A silent zero (score 0, no grader detail, no `error`) and an all-zero run are also exit 7 (#735).
  - The token expires after a year: rotate the secret. Anyone who can read it can use the plan, so keep it in the protected environment with required reviewers and never expose it to `pull_request` runs.
  - The plugin-evals page documents `ANTHROPIC_API_KEY` for CI and says eval uses "the same authentication" as normal sessions; it does not name `CLAUDE_CODE_OAUTH_TOKEN`. Confirmed by the first full dispatch (2026-11-03, [run 41756776006](https://github.com/dfadler/agent-config/actions/runs/41756776006), #648): the token worked, every case scored with a cost and no `arms.with[].error`.
- **Plugins without `evals/`:** the `plan` job warns and lists any plugin with `skills/`, `agents/` or a root `SKILL.md` but no `evals/` (#648), so a gap shows in the step summary instead of the plugin silently dropping out of the matrix. Warn-only.
- **Plugin-arm-only agent cases** (`shell-script-reviewer`, `vite`'s reviewer, `adversarial-reviewer`, `docs-staleness-checker`, `playwright`'s agent, `vitest`'s investigator): the no-plugin arm cannot dispatch a plugin agent, so these cases run `--ablation none` and have no Δ. They are gated by the absolute pass bar (wrapper exit, every grader passes) and the checker's validity checks, not by Δ; the checker skips cases with no `delta` under the Δ floor (#585). Decision (#648): **make the pass bar itself strict (c) first.** Each case carries free deterministic graders on the report contents: dispatch (`tool_used` Agent), setup files (`file_exists`), report-only (`tool_used` Write min/max plus a `regex` on the reviewed file still containing the planted defect), and one `regex` on `last_message` per planted defect, anchored on a token from the fixture. **Escape hatch (b), a with-arm-only threshold below 1, only for a case that stays noisy after that**, meaning a grader that fails on a correct report because the wording varies and cannot be narrowed to a stable token. It is not implemented: the wrapper takes one `--threshold` per tier (`tiers.ts`) and passes it to every per-case `claude plugin eval` invocation, so a per-case value needs a per-case setting in the wrapper. Until then, narrow or split the noisy grader (lowering its `weight` does not help: at threshold 1 every positive-weight grader must still pass), and record the noisy case in the issue before asking for the wrapper change.
- **Weekly run and alerting (#738):** not a GitHub cron. A local Claude scheduled task (`plugin-evals-weekly`, Mondays 09:00 local) runs the wrapper per plugin from a detached `origin/main` worktree, checks the plugin's `aggregate-result.json` files with one `check-plugin-eval.ts` call (all files as arguments; one call per file keeps the delta gate advisory), and saves results under `~/.claude/plugin-eval-results/<date>/` (a local baseline). It runs only while the Claude app is open, and runs on next launch if missed. Its session summary is the alert for that local run. A `workflow_dispatch` run that fails or is inconclusive also opens (or comments on) one "Plugin evals failed" issue via the `notify` job, using `GITHUB_TOKEN` only.
- **Ungated cases (#738):** the `Check results` step (one checker call over all result files) lists every case with no `delta` in the step summary, so a plugin-arm-only case shows as ungated by delta instead of being skipped silently.
- **Committed baseline (#738, option C):** `evals/results/` is gitignored and artifacts expire after 30 days, so a score of record is saved by hand. After a finished run, `node plugins/eval-authoring/scripts/ts/save-baseline.ts [--tier NAME] <run dir or aggregate-result.json>` writes `docs/eval-baselines/<plugin>.json` (plugin, date, version, tier, model and judge model, mean with/without score, mean Δ, all-runs-pass share (`passK`), per-case scores), and you commit it. `--out docs/eval-baselines/<plugin>-v1.0.0.json` keeps one file per release; it will not overwrite a file without `--force`, and it refuses a partial, errored or implausible run. It reads results only: no workflow edit, no secret, no CI write path.
- **Judge model (#738), open:** `DEFAULT_MODEL` and `DEFAULT_JUDGE_MODEL` in `tiers.ts` are both `claude-sonnet-5-5`; changing the judge shifts every score, so recalibrate Δ first. The paid judge-model A/B is not part of the baseline-script change.
- **Timeout (#648):** the `eval` job has `timeout-minutes: 30`, a cap, not a budget to raise. A suite that cannot finish inside it is configured to fit: fewer cases, more concurrency (CI passes `--jobs 6`, the wrapper's pass-through of the CLI's `-j` (1 to 8; the CLI default is 1, so CI ran serially before)), or a split matrix entry. The wrapper call is wrapped in `timeout --signal=INT --kill-after=1m 24m`, a deadline shorter than the job timeout. A suite that outlasts it ends through the deadline (GNU `timeout` exits 124, or 137 after the KILL; the Check step maps any code other than 0 and 1 to inconclusive), so the Check and Upload steps still run and the results of finished cases are kept; a job-level cancel would otherwise skip them. As a backstop for a hang outside the wrapper (setup, install, Check), Upload runs on `always()` and `notify` also fires when `eval` is `cancelled` (#889); a manual cancel opens the issue too. On the INT the wrapper stops launching cases, forwards INT to the `claude` run in flight, writes `run-evals-summary.json` with the unstarted cases listed, and exits 7, but `timeout` still reports 124, so the Check step sees inconclusive either way; the summary is what tells a reader which cases never ran. Finished per-case results stay. Sizing: the 2026-10-19 eval-authoring run took 23.8 minutes for at most 13 of its 21 cases (at least 108 s per case at the wrapper's default concurrency), so 42 cases need about 76 minutes without `--jobs`. Measured: with `--jobs 6` the first full dispatch ran all 38 eval-authoring cases in 15.7 minutes (01:51 to 02:07 UTC) for $17.46 list price, inside the 24 minute deadline and the $25 ceiling. The same run was the first to show the Run evals step exiting before `cli-exit` was written when the wrapper exited non-zero, which skipped Check results (#906, fixed in #925). Its result: wrapper exit 1 (19 of 38 cases below the pass threshold), mean Δ +0.44 over 38 cases (above the 0.14 floor), mean with-plugin score 0.77, and `diagnose-scores-cutoff-verdict`, `diagnose-scores-fires-on-exit-2-fine-results` and `run-evals-fires-on-wrapper-command-request` scored 0 on every run. The checker then called the run inconclusive (exit 7) and `save-baseline.ts` refused it, because the all-zero test looked at one file (one case) at a time; it now looks at the pooled run, so those cases are reported as failing cases and the run can be baselined.
- **Baseline cache (#855):** the wrapper stores each two-arm case's without arm under `evals/results/.baseline-cache` and reuses it on a later run with the same key. CI never hits it: `evals/results/` is gitignored and empty on a fresh checkout, and nothing restores it, so the gate always reads a delta the CLI computed from two arms in one invocation. `--no-cache` turns it off locally.
- **Concurrency:** `group: plugin-evals`, `cancel-in-progress: false`.

Open owner questions (weekly spend, a capped key) are listed in the comment; the Δ floor is settled at 0.14 (#736).
